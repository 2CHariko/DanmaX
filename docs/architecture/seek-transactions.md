# 公共定位事务（SeekController）

视频定位（Seek）与历史续播恢复由应用层唯一的 `SeekController` 统一编排；播放器后端仅负责提交传输命令、报告回执与提供新鲜采样。独立弹幕任务使用本地单调时钟，不进入媒体定位事务。

> [!IMPORTANT]
> 原始传输回执（`seekFinished`）仅表示命令是否送达通信通道或测试注入，不能作为产品层的定位成功事件；UI 与业务层仅消费 `SeekController` 产出的 `landed` / `finished` 状态。

## 1. 传输结果与确认语义

后端通过 `SeekDispatch` 报告请求 ID、发送前的新鲜时间轴、实际发送与返回单调时间以及三态结果：

| 结果枚举 | 含义 | `SeekController` 处理策略 |
|---|---|---|
| `Rejected` | 前置校验拒绝、目标无效或播放器明确拒收 | 立即结束该请求并展示具体原因 |
| `Submitted` | 消息或接口已受理请求，但尚未到达目标位置 | 阻塞等待发送之后的新鲜位置读回 |
| `Unknown` | 消息超时或响应无效（播放器可能已经执行） | 保持等待确认，严禁盲目自动重发 |

### 确认与精度规则

1. **绑定与新鲜度校验**：确认过程绑定当前连接、内容 ID 与请求 ID，并排除发送前旧采样与未变化的滞后位置，使用实际发送单调时间界定播放推进。
2. **精度区分**：
   - 声明 `Precise` 精度的后端（如 VLC 公开时间接口）要求读回位置落入目标容差范围内。
   - 声明 `Unspecified` 的后端（如当前 PotPlayer 消息）在观测到位置跳变并稳定于新轨迹后报告实际落点，严禁把较大误差包装为精确到达。
3. **弹幕重置**：弹幕引擎始终以播放器实际反馈的时间轴为准进行重置，不以预览草稿位置驱动投放。
4. **通道超时策略**：PotPlayer 状态查询保持 100 ms 工作线程上限，定位消息单独使用 500 ms 上限（超时且实例仍有效时报告 `Unknown`）；VLC 保留 URI 与播放列表项服务端校验，传输失败报告 `Unknown`、明确拒绝报告 `Rejected`。

## 2. 连续输入合并与超时管理

- **串行与排队**：同一时刻最多允许**一条正在执行（in-flight）的请求**与**一条最新的待执行意图（pending intent）**。连续拖动仅替换尚未发送的意图，前一条请求未确认前禁止并发提交；当前请求确认后，以最新时间轴提交最终目标。
- **确认与迟到观察窗口**：默认确认窗口为 **8 秒**。超时仍未确认时向界面提示结果未知，不自动重发，也不自动推进后续待执行意图；额外保留最多一条 **8 秒** 的迟到观察记录，若同一请求随后确认完成则仅清除对应提示。
- **状态清理**：新请求、内容切换、任务结束或实例退出时立即清理全部等待与迟到观察状态。
- **协议固有边界**：对于无命令回显 ID 的播放器协议，无法承诺拦截所有播放器外部并发定位，也不能保证跨异常的“恰好一次执行”。

## 3. 界面交互契约

- QML 进度条在鼠标拖动期间仅缓存草稿目标用于预览，松手时提交所缓存的草稿值；松手后禁止重新读取可能已被属性绑定覆写的 `value`。
- 等待定位确认期间保留最新目标预览并允许用户继续发起新定位，实际播放时间轴仍独立来自后端采样。
- 近似落点反馈时短暂显示实际落点时间，不使用连接警告替代定位结果提示。

## 4. 验证要求

- **单元测试与夹具**：须覆盖消息超时但实际执行、异步回执乱序、旧缓存位置拦截、`Precise` 与 `Unspecified` 区分、迟到完成、连续目标合并、任务取消与历史恢复。Win32 延迟夹具仅验证 IPC 与请求计数，不能替代真实播放器解码。
- **实机验证**：真实播放器验证须覆盖长 MKV/MP4、大跨度前后跳转、播放/暂停状态定位、连续拖动、网络或映射路径以及界面松手不回弹，并如实记录已验证范围。
