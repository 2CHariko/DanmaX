# libVLC 内嵌单文件分发可行性

日期：2026-10-18。对象为当前 C++20／Qt 6.11／Windows x64 工程与锁定的 libVLC 3.0.23。本轮仅进行代码、已缓存发行归档和官方资料分析，没有改动播放器、构建或发布行为，也没有完成静态 libVLC 编译／单文件实播验收。

## 结论

**一个 EXE 下载后自行释放 libVLC 运行库，工程上可行；一个 EXE 直接运行且不释放 DLL／插件，有源码机制支持，但在本项目 MSVC 工具链上尚未证实。后者应作为独立构建研究，不能视为现有打包脚本的小改动。**

当前项目对静态便携版的既有要求是“无需释放运行库”，允许旁置配置、日志和缓存。自解压改变了这个交付条件，不能用它代替纯单 EXE 并继续声称满足原条件。

建议沿原条件先验证“静态 libVLC＋静态插件能否链接进现有 MSVC 主程序”，通过后再扩大编解码支持。如果允许运行时释放依赖，可选择成本较低的自解压路线；这是一种单文件分发格式，运行后仍有 DLL／插件目录。

后续补充：若接受播放器内核作为另行安装的可选组件，建议优先评估本文末尾的“手动导入／按需下载”路线。它可以保持主程序单 EXE，绕开 libVLC 全静态链接问题，但安装后的运行环境包含组件文件。

| 路线 | 单文件交付 | 不释放运行库 | 对现工程的可行性与状态 |
| --- | --- | --- | --- |
| 静态 Qt 主程序＋旁置 libVLC | 主程序是单 EXE；内置播放另需组件 | 无解压步骤，但依赖旁置文件 | 本机隔离探针通过；正式 CMake 与打包规则仍禁止此组合 |
| EXE 内嵌归档，启动时解压 DLL／插件 | 是 | 否 | 可复用现有 CAB／FDI 基础；尚未实现 libVLC 版本，也未形成分发清单 |
| 静态 Qt＋静态 libVLC／core／所需模块及第三方库 | 是 | 是 | 上游源码有静态机制；Windows 工具链、最终链接及播放能力待探针验证 |
| DLL 放入资源，依靠普通 QLibrary 直接从内存加载 | 是 | 表面目标为是 | 现有加载机制不能实现；需要额外 PE 加载／路径虚拟化能力，不建议采用 |

这里的“不释放运行库”不排除 Windows 系统 DLL、驱动和系统字体，也不等于没有配置、缓存或临时文件写入。

## 当前工程已经具备什么

- `LibVlcBackend.cpp` 以绝对路径 `applicationDirPath()/libvlc/libvlc.dll` 加载公共 C API；通过 `AddDllDirectory` 注册依赖目录。`preflight()` 要求实际存在 `libvlc.dll`、`libvlccore.dll` 和 `plugins/`。
- C API 由唯一后台线程串行使用，视频输出保持现有 HWND，媒体任务、SeekController、弹幕引擎和覆盖窗已接入。改变链接方式不需要重新设计媒体业务或改成视频帧回调。
- `deployment.ps1` 的 libVLC 开发部署复制整个锁定归档目录，包括头文件、VLC 自身 EXE、其他界面和通知文件；这是验证用完整组合，不是产品最小运行库。
- `CMakeLists.txt` 明确禁止同时启用 `DANMAKU_STATIC_QT` 和 `DANMAKU_ENABLE_LIBVLC`。当前正式 libVLC 预设仍采用动态 Qt；静态 Qt 与动态 libVLC 组合仅在下方隔离探针中验证。
- `package.ps1` 同时检查预设与实际缓存，拒绝将内置构建打包；`release.ps1` 沿用现有未启用内置功能的发布预设。
- `src/portable/main.cpp` 和 `scripts/portable.ps1` 已有 Windows CAB 自解压、包摘要目录、互斥锁、逐文件 SHA-256 校验、损坏目录保留与子进程启动。现实现释放整个动态 Qt 主程序，不是仅释放 libVLC 的同进程方案。

现有内置播放的实机记录见 [接入报告](LIBVLC_INTEGRATION.md)，其中的开发版实播不能替代新链接方式和新部署包的验收。

## 真正静态链接为什么值得试、又为什么不能直接承诺

本轮以锁定源码归档为准，查到以下机制：

- `configure.ac:554` 的 libtool 默认配置为共享库并关闭静态，但可配置；`:562` 对关闭共享库的限制同时检查 `enable_vlc`，因此研究对象应为禁用完整 VLC 应用后的 libVLC，而不是把完整 VLC 桌面程序静态塞入。
- `configure.ac:841` 在关闭共享库时关闭动态模块能力；`modules/common.am:21` 根据动态／静态模块切换入口宏。
- `include/vlc_plugin.h` 为静态模块生成带模块名的入口；`src/modules/bank.c:179` 在非动态插件配置下读取 `vlc_static_modules[]` 并注册内置模块。
- `lib/Makefile.am:58` 显示 libVLC 还依赖 core、compat 等库，仅产出公共 API 静态库并不足够。

这些是“存在静态实现基础”的证据，**不是 Windows 全静态构建成功的证据**。上游同版本 [Windows 构建脚本](https://github.com/videolan/vlc/blob/3.0.23/extras/package/win32/build.sh) 采用 MinGW 目标、GNU／Clang 工具和 contrib 构建体系，与当前 MSVC Qt SDK 的构建链不同。锁定发行源码中的行号以上述本地抽样为准，上游仓库用于交叉参考。

需要解决的边界包括：

1. **最终链接与运行时 ABI。** libVLC 对外是 C API，有利于隔离接口；但内部模块和依赖可包含 C++。不能由此推出 MinGW 的 C++ 异常、运行时、TLS、线程库和静态对象都能与 MSVC `/MT` 直接合并，也不能反过来断言所有 COFF 对象必然不能混链。必须用目标工具链实测。
2. **静态模块注册和链接保留。** 需要由明确模块清单生成入口数组，并处理静态库按需抽取、循环依赖和链接裁剪。库里“有解码器”与启动后“能找到解码器”是两件事；Qt 的静态插件导入不能替代 VLC 模块注册。
3. **传递依赖和动态加载。** avcodec、字幕、字体、音频／视频输出等所选路径必须审计。主 EXE 导入表没有 `libvlc.dll`，仍不能证明插件不会在播放期间加载其他可分发 DLL。
4. **资源及路径。** 禁用 Lua／外部界面并不自动取消所有数据文件需求。字体发现、字幕和可选音效资源须逐项确定能使用系统资源、嵌入资源还是禁用；不能暗中恢复依赖目录。
5. **构建可复现性。** 官方二进制 ZIP 不是静态 SDK；源码 TAR 也不能等同于已齐备第三方依赖源码、编译器与工具。新增工具和 contrib 均须独立锁定版本、来源、SHA-256、许可和项目内缓存，准备完成后离线构建。

直接将现有 DLL 编入 `.qrc`／PE 资源只改变存储位置。微软的 [LoadLibraryExW](https://learn.microsoft.com/en-us/windows/win32/api/libloaderapi/nf-libloaderapi-loadlibraryexw) 使用模块文件路径，并不提供从任意资源字节载入 DLL 的普通 API。自行实现 PE 加载还需处理依赖、重定位、TLS、异常展开及 VLC 自身的插件路径逻辑，维护范围远超本项目打包需求，不纳入建议路线。

## 自解压路线的具体改造量

如果产品条件改为“只分发一个 EXE，允许运行库落地”，可采用两种实现：

- **复用现有启动器。** 先形成通过验收的内置播放器目录包，再将该目录作为 CAB 载荷。原启动器释放的主程序旁保留 `libvlc/`，与现后端路径最接近。仍有启动器和子主程序，现动态 Qt 载荷还保留其 VC++ 运行库前提；必须单独验证新载荷的依赖。
- **静态主程序只释放 libVLC。** 用静态 Qt 主程序携带归档，在首次使用内置播放器前解压到明确的数据缓存目录，验证完整性后交给后端加载。没有第二份 Qt 主程序，但需新增资源解压入口、后台准备状态、运行库路径提供者及多实例协调。当前固定的 `runtimeDirectory()` 和 CMake 组合限制都须调整。

两种方式都应按完整运行库版本／摘要隔离，不覆盖进程正在使用的 DLL；解压到临时目录，逐文件验证完成后再提交可用目录，失败保留当前任务。TEMP/TMP、运行缓存和清理范围遵守项目约束，不搜索系统 VLC，不改永久 PATH。外部环境的 `VLC_PLUGIN_PATH` 等还需按所选实现隔离，避免载入全局插件。

逐次全量校验、冷启动解压及防病毒扫描会影响启动开销，必须分别测量冷启动、复用和修复；不能沿用旧 Qt 包成绩。模块裁剪若改变文件集合，不能继续使用不匹配的插件缓存。新包要明确选择运行时扫描或匹配清单的缓存生成方式。

现启动器会修复被修改的 DLL，不能把“有动态库”直接等同于已满足用户替换／修改库的条件；需要提供经过验证的重建路径或满足相应许可的替换方式。

## 分发材料边界

libVLC 为 LGPL-2.1-or-later，不代表完整 VLC ZIP 中每个插件和第三方组件都是同一许可证。VideoLAN 的[模块重新许可说明](https://www.videolan.org/press/lgpl-modules.html) 使用的是大部分模块这一范围。应按实际纳入清单审查，不按目录名字猜测许可。

本项目已有 GPLv3 发布定位，静态链接并不天然禁止；仍须核对每项组件的版本和兼容性，不能把项目 GPLv3 当作所有依赖自动兼容的证明。对 LGPL 静态组合，应提供对应源码及可实际修改库、重建／重新链接程序的材料；分发动态库同样有对应源码等义务。[GNU 官方 FAQ](https://www.gnu.org/licenses/gpl-faq.en.html#LGPLStaticVsDynamic) 对两种方式均有说明。

现有 libVLC 源码归档不能直接宣称覆盖整份 Windows 二进制中所有 contrib 对应源码及补丁。发布材料至少需增加实际模块与第三方库清单、许可通知、匹配源码／补丁、完整工具链和构建选项；只有验证能重建对应组合后，才可声明这一部分交付完成。运行入口为单 EXE 与公开分发另附源码、许可和重建材料不冲突。

## 下一步验证门槛

以下均为建议，尚未实施；本轮不安装工具链、不下载新依赖、不解除发布保护。

1. **先验证与 MSVC 的链接。** 项目内独立 `out/build/` 目录构建最小静态 core／libVLC 和少量静态模块；用明确配置的 MSVC 消费端验证链接、实例创建、模块注册、正常释放。先验证工具链边界，避免先投入全量编解码构建。若目标 ABI 不成立，记录具体阻塞；更换整个 Qt 工具链需另作决策，不静默切换。
2. **再验证最小实际视频链。** 明确封装、编码和字幕目标，首批可用现有 HEVC／AAC MP4 与 AVI 样本，再补 H.264、MKV、软解回退及字幕。保留当前 HWND／D3D11 路径，记录实际所用模块。完整模式未验证的格式不承诺支持。
3. **接入独立静态组合预设。** 用编译期选择的 API 装载策略替代单一路径 QLibrary 装载；纯静态模式不再要求 DLL／plugins 目录。保留原开发预设，并验证静态 Qt 组合、公共后端契约、定位／历史、切换独立弹幕和退出释放。
4. **验证分发包。** 仅系统 PATH、无已安装 VLC／Qt 的干净 Windows；EXE 搬迁、中文空格路径、不可写缓存、多实例、冷／热启动、长播与故障释放。覆盖暂停、跳转、硬／软解及字幕期间的模块审计和文件创建记录，排除运行时 DLL／EXE／插件释放。仅检查主导入表不足以验收。
5. **形成实际数字后再发布。** 记录 EXE 大小、构建环境、冷／热首屏、首次出画、内存与硬解情况；完成组件清单和对应分发材料后，再调整 package／release 的能力检查。

若第 1 步未通过，当前结论仍是“纯单 EXE 研究受阻”，不能改称“已经打包可用”。自解压则可在允许释放运行库的条件下另行实施。本轮确认的是源码机制、现工程改造边界与原始体积；最终体积、静态实播、性能和干净系统分发均未验证。

## 可选组件：手动导入与 GitHub 按需下载

针对后续问题，两种安装来源均可行，适合作为接受旁置组件后的优先路线：**主程序静态 Qt 单 EXE，内置播放适配代码编入主程序，libVLC 原生运行库另行安装。** 不需要把 LibVlcBackend 再封装成 Qt 插件；当前公共 C API 动态加载已经提供所需边界。这样能避开把 MinGW C++ 运行时与 MSVC 静态对象合并的问题，但仍须验证实际 DLL 组合。

这里的组件是同一构建的一整套 `libvlc.dll`、`libvlccore.dll`、必要的 `plugins/`、其他运行依赖及许可材料，不是导入一个 DLL，也不是允许任意第三方插件。不同发行版的 core 和插件不能混用。

| 安装来源 | 用户流程 | 实施边界 |
| --- | --- | --- |
| 手动导入离线包 | 选择受支持的组件归档，验证后安装 | 适合离线／GitHub 不可达环境；优先支持明确包格式和已知版本，不要求用户挑 DLL |
| GitHub Releases 下载 | 在内置播放器组件入口选择下载，自动下载、验证、解包、安装 | 使用受控仓库固定 tag／asset；不下载仓库源码 ZIP，不自动追随 `latest` |
| VideoLAN 官方归档 | 使用锁定官方下载地址获取已验证归档，再走同一安装流程 | 当前锁已有官方 Windows ZIP 与 SHA-256；原包较大，产品裁剪和对应材料仍需验证 |

GitHub 的 [Release assets API](https://docs.github.com/en/rest/releases/assets) 提供下载地址及摘要字段，也支持重定向下载；[固定发布链接](https://docs.github.com/en/repositories/releasing-projects-on-github/linking-to-releases) 可以直接指向指定 tag 的附件。不能据此假定 VideoLAN 的 GitHub 源码镜像已经发布本项目所需的 Windows 运行库附件。若使用 GitHub，可由项目维护独立组件 Release，并承担该组件包的来源、校验、许可和版本维护。

首版可以内置经过审查的组件版本、目标架构、来源 URL、包 SHA-256 和包格式，直接下载固定附件，无需每次启动查询 API，也不要求用户填写 GitHub Token。GitHub API 对匿名请求有[频率限制](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)，网络失败时保留离线导入入口。摘要应以程序内的受信清单为准；未来允许独立更新清单时再设计签名验证，不能只依赖与下载包一起取得的散列文本。

建议的安装位置如下，均相对程序／明确的数据根定位，最终目录名由组件清单生成：

```text
DanmaX.exe
modules/libvlc/<version>-windows-x64/<package-hash>/
  libvlc.dll
  libvlccore.dll
  plugins/
  component.json
  licenses/
cache/downloads/       下载中及可重试的归档
```

安装后的 `modules/` 是运行依赖，不应作为可随手清理的下载缓存。搬迁主程序时要同时携带组件，或者到目标位置重新安装。使用自定义数据目录时保持路径规则一致；位置不可写明确失败，不静默退回用户级安装。主程序初始下载体积可保持较小，但使用内置播放后仍需下载和占用组件空间。

手动与自动入口共用以下流程：

1. 验证受支持版本、Windows x64、应用兼容范围、包摘要和容量限制，再解包；拒绝越界路径、链接逃逸及超出声明范围的文件。
2. 在独立临时目录完成安装，检查文件清单和实际架构，成功后提交可用目录；取消或失败不改变当前任务／已有组件。目录操作及清理严格限定在已验证的组件产物范围。
3. 未安装时显示组件未安装及下载／导入动作，不隐式打开其他播放器；安装完成后可在下一次打开视频时使用。后台准备不在 QML 中实现，不阻塞 GUI。
4. 采用绝对路径和受控 DLL／插件搜索路径，不依赖系统 VLC、永久 PATH 或其他项目目录。加载 DLL 本身会执行原生代码，因此必须在完整校验后才加载，不能通过先加载未知 DLL 判断它是否可信。
5. 新版本旁路安装，不覆盖已加载 DLL。首版将已加载组件的更新延后到应用下次启动激活，保留旧版以便失败回退；不尝试播放期间卸载、替换 core 或插件。
