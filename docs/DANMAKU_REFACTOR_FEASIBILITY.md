# 弹幕引擎重构与 NipaPlay 移植可行性

日期：2026-10-07。状态：源码分析与建议，未实施、未运行上游或性能对比。

后续实施说明：本报告保留选型时的分析；当前已完成时钟、物理轨道索引、紧凑快照、窗口帧驱动及受限图片后端原型，最新验证见 `FRAMEWORK_STATUS.md` 的重构增量。未移植上游源码、未引入 Rust/wgpu。预取、完整性能矩阵与原生后端仍未实施，不属于已验收能力。

上游基线：AimesSoft/NipaPlay-Reload `adc9bb55852b89b5f89fd4e5228ceb6713406c18`。
当前项目基线：现有工作区源码及 `FRAMEWORK_STATUS.md`。本报告不改变既有架构约束或验收状态。

## 结论

可重构，推荐移植设计、在当前 C++20 / Qt Quick 架构内实现；暂不整体引入 Flutter、Rust/wgpu 或上游播放器。

最值得吸收的是媒体时钟与渲染节奏分离、时间窗口索引、布局结果与绘制资源分离、预取与缓存回收、低频场景变更和逐帧运动分离。语言不是障碍，宿主耦合、图形资源交接和文字兼容性才是主要成本。

现有 2000 条压力记录表明需要优化，但没有定位 CPU/GPU 瓶颈，不能据此认定换后端会更快。

## 上游实际结构

- `lib/danmaku_abstraction/danmaku_kernel_factory.dart`：支持平台默认 DFM+，Web 等平台及 Linux NVIDIA 默认选择其他路径；这是源码策略，不是本项目验证结果。
- `rust/src/api/dfm_plus.rs`、`rust/src/dfm_core/`：测量、过滤与预计算轨道布局。
- `lib/danmaku_dfm/dfm_plus_layout_bridge.dart`：Dart 侧二分查询时间窗口、对象复用；不能只提取 Rust 就获得完整默认行为。
- `lib/danmaku_dfm/dfm_plus_overlay.dart`：媒体时间、单调时钟、跳转代次、暂停与倍速，约 50ms 场景提交、250ms 运动前瞻、3 秒字形预取。参数不是性能成绩，也不建议原样照搬。
- `rust/src/next2_engine/`：原生时钟、wgpu 渲染、字形/emoji 图集、C ABI 与平台呈现。
- 旧 `docs/gpu_danmaku_findings.md` 对应另一套实现，不能作为当前 DFM+ 缺陷清单。

## 当前实现对照

| 当前位置 | 已有能力/观察 | 重构方向 |
|---|---|---|
| `src/core/DanmakuEngine.cpp` | 排序游标、seek 二分定位、有界活动池、固定/滚动共享物理轨道 | 保留语义；按轨道维护占用索引，避免每次尝试轨道都遍历所有槽位 |
| `Engine::tick` | 增量移动；过期投放超过 0.4 秒丢弃；引擎内部还判断跳转 | 明确时钟事件与迟到策略，统一跳转入口，减少与应用层重复判断 |
| `src/application/AppController.cpp` | SMTC 样本外推；固定 16ms QTimer 同时驱动调度和呈现 | 提取媒体时钟；绘制使用窗口帧节奏，低频媒体采样与前台检查独立 |
| `src/renderer/DanmakuItem.cpp` | QTextLayout 缓存；每条 Transform + Text 节点；逐帧遍历并更新矩阵 | 紧凑活动快照，资源与位置分离；保留现有后端作为基准 |
| 描边 | 1px 使用 Outline；大于 1px 使用八份黑色文字加正文 | 单独测量粗描边成本，不能混用不同描边条件宣称提速 |
| 缓存 | 布局估算 16MiB；活动对象最多 5000 | 分开记录布局、图片/图集、活动引用及实际 GPU 资源的可观测范围 |
| 测试 | 已覆盖暂停、跳转、共享轨道、容量边界 | 用现有测试约束重构，再补新增时钟、失效与回收场景 |

`present()` 当前按池容量遍历，`spawn()` 最坏按候选轨道数 × 池容量扫描；这些是源码上的成本，不是已测得的主瓶颈。
当前基准允许重叠且描边为 1px，不能用防碰撞扫描或九文字节点解释该基准的全部退化。

## 三条路线

| 路线 | 可行性 | 主要代价 | 建议 |
|---|---|---|---|
| 借鉴设计，C++ 核心 + Qt 公开场景图 | 高 | 时钟/索引/快照重构及回归验证 | 首选 |
| 提取 Rust 调度库，Qt 继续渲染 | 有条件 | 清理 flutter_rust_bridge 等耦合；新增稳定 C ABI、Cargo 工具链与分发管理；Qt 测量结果需作为输入 | 当前没有证明优于 C++ 重写的收益 |
| 提取 Rust/wgpu 渲染，接 Qt 或独立覆盖窗 | 有条件、风险最高 | 双图形栈、共享纹理同步、设备选择/丢失、DPI、窗口呈现、字体塑形、部署 | 仅在 Qt 路线实测瓶颈明确后做隔离原型 |

上游已有 C ABI 和 Windows DX12 共享纹理代码，但它不是可直接插入 Qt 的接口。必须验证实际 Qt 图形后端、适配器、同步和所有权；不能宣称零拷贝、无阻塞或跨后端兼容。
`next2_engine_set_frame` 接收 JSON 后发送渲染命令，再 `reply_rx.recv()` 同步等待。直接从 GUI 帧回调调用有阻塞风险；若采用该后端，应另设计有界队列、过期代次拒绝和取消/退出协议。

## 推荐结构

保持少量构建目标，不为每个概念新增独立库：

1. **媒体时钟**：接收位置、采样时刻、播放速率、状态、媒体身份；输出统一时间锚点和代次。暂停冻结、恢复重置墙钟基准、超时冻结、显式 seek 清空。SMTC 没有明确 seek 事件时仍需容差判断，不能套用内置播放器事件假设。
2. **时间轴与轨道**：纯 C++，输入不可变弹幕数据、文字测量和区域参数；保留单调游标。每轨道维护占用信息与回收条件；跨类型按物理区域避让。只有引入不同滚动速度时才扩展追尾算法。
3. **场景快照**：包含代次、样式版本、时间锚点以及紧凑活动记录。移交新增/删除与运动参数；渲染侧拥有同步后的副本，绝不读取 GUI 线程正在修改的 Engine。
4. **文字服务**：继续用 Qt 完成文字布局与字体回退。资源准备从热点路径移出，设置每批工作量；未确认字体对象/设备线程规则前，不把现有 QTextLayout 直接搬到工作线程。
5. **渲染后端**：保留 QSGTextNode；另做整条文字图片缓存原型。图片/图集批量绘制仅在证据支持时增加，全部通过公开 Qt Quick 能力实现。

窗口帧驱动必须能连续请求后续帧，不能只是删除 QTimer；隐藏或空屏停止绘制，但媒体采样继续。所有场景图和 GPU 资源仍在 Qt 规定阶段访问。

## 不应原样迁移的策略

- **全量预布局**：适合离线固定字体和区域，但百万条、字号/屏幕改变时有重算成本。先采用增量轨道与有界预取；后续可独立比较分块预布局。
- **跳转重建在屏弹幕**：上游可从时间窗口重建，当前契约是清空并从目标开始。第一轮保持现有契约，不把重构变成隐式产品行为变更。
- **不同类型分开避让**：当前固定/滚动共享物理轨道，不能退化为各管各的。
- **逐字符渲染**：上游普通文字路径按 `text.chars()` 查字形、累加 advance，不能直接替代完整文字塑形。复杂脚本、组合字符、双向文字、emoji 必须专项验证。
- **图集就是更快**：Qt 自身已有文字资源复用，现有代码也没有每帧重新排版。先分离节点、同步、绘制和首次布局成本，再决定换缓存形式。
- **整条文字图片无成本**：按 `宽 × 高 × DPR² × 4` 估算 RGBA 图片成本；重复文本复用、字节预算、活动引用、逐帧上传预算及字体/DPI失效必不可少。

## 实施与验收顺序

### 1. 可重复基线

固定样本、分辨率、DPI、刷新率和构建类型；记录真实图形适配器/后端。分别测重复文字、独立文字、长文本/emoji，1px/粗描边，500/2000/5000 活动数；5000 仅是压力场景，不是承诺。
区分核心调度、文字准备、GUI同步、场景图更新、实际呈现和GPU指标，未采集到的指标明确留空。

### 2. 时钟、轨道与快照重构

保持原后端，验证输出语义一致。补充低/高倍速、暂停恢复、微小回退、大跳转、稀疏/过期样本、隐藏恢复、同帧大量投放、窗口/DPI/字体变更和旧代次结果到达。
核心由 CTest 驱动；Qt 生命周期和缓存用 Qt 相关测试；实机行为不能用 offscreen 替代。

### 3. 图片缓存后端对照

相同调度、样本和配置比较帧时间分布、首次出现卡顿、内存/GPU资源、文字质量、缓存抖动及空闲消耗。新后端只有在目标负载有明确收益且无显著兼容性回退时才替换默认。

### 4. 条件性的原生后端原型

前三步证明 Qt 公开方案无法满足目标后，再评估 Rust/wgpu；先验证空透明窗、共享纹理及暂停/退出，再加载压力场景。此路线需要架构决策、依赖准备与部署说明，不能随常规构建联网安装。

## 依赖与许可证

建议路线无需新增运行时依赖。若引入 Rust：工具放 `.tools/`、依赖放 `.deps/` 或项目缓存、Cargo 缓存与构建产物显式项目内定位；固定工具和依赖版本、哈希与来源，准备步骤独立，离线/锁定构建，不修改永久 PATH。
